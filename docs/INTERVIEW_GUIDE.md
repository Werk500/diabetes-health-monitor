# 秋招面试讲解手册

## 1. 两分钟项目介绍

> 这是一个面向糖尿病患者的全栈健康管理系统，后端使用 Spring Boot 3、Spring Security、MyBatis-Plus、MySQL 和 Redis，前端使用 Vue 3。
>
> 项目除了常规健康记录，还实现了三个我认为比较有含金量的部分。第一，血糖指标不是交给 AI 计算，而是用确定性 Java 代码计算 TIR、TAR、TBR、CV 和 GMI，AI 只负责解释结果，避免医疗数值被模型编造。第二，认证从单个长期 JWT 改成了 15 分钟 Access Token 加 7 天 HttpOnly Refresh Token，使用 Redis 哈希存储、Lua 原子轮换和用户版本号处理并发刷新、改密与禁用下线。第三，Excel/PDF 导出是异步任务，使用数据库状态机、条件更新领取任务、PENDING 补偿和 RUNNING 超时恢复，并通过 Prometheus 暴露积压、失败率和 P95 耗时。
>
> 项目还接入了 SSE 流式 AI 对话、食物图片识别、每日聚合任务和 Grafana 监控，并有 91 个后端测试和 GitHub Actions CI。

## 2. 一张图讲清系统

```text
Vue 3
  → REST/SSE
Spring Boot 模块化单体
  → MySQL：业务主数据
  → Redis：Token/缓存/限流/锁/会话
  → DashScope：AI 解释与多模态识别
  → Prometheus/Grafana：可观测性
```

关键表述：

- 当前是模块化单体，不是硬凹微服务。
- 业务边界已经分成 Auth、Records、Analytics、AI、Export、Admin。
- 优先保证一致性、可测试性和排错效率，后续可以按边界拆分。

## 3. 高频问题与回答

### Q1：为什么没有直接做成微服务？

回答：

> 当前业务的数据关联度很高，比如血糖明细、聚合数据、趋势和导出都依赖同一份健康数据。单库事务和单进程排错更适合这个规模。项目内部已经按控制器、服务、任务和领域计算器拆清边界，后续如果访问量上来，可以优先拆出 Auth、Analytics、AI 和 Export。过早拆微服务会把精力耗在注册中心、分布式事务和链路治理上。

### Q2：为什么用短 Access Token 加长 Refresh Token？

回答：

> 单个 24 小时 JWT 一旦泄露，风险窗口太长，而且服务端无法主动吊销。现在 Access Token 只有 15 分钟，用于无状态接口认证；Refresh Token 是 7 天随机串，存 HttpOnly Cookie，Redis 只保存它的 SHA-256。这样长期凭据不暴露给 JS，也能主动删除和轮换。

### Q3：为什么 Refresh Token 不也用 JWT？

回答：

> Refresh Token 需要强吊销、一次一换和 Redis 会话管理。随机不透明串更直接：Redis 存在就是有效，删除就失效。JWT 适合短期的 Access Token，不代表所有 Token 都应该是 JWT。

### Q4：两个请求同时刷新怎么办？

回答：

> Refresh Token 的消费使用 Lua 做原子 `GET + DEL`，两个请求只有一个能读到映射。另一个直接 401。然后新 Refresh Token 带有用户当前 version，改密或禁用会递增 version，旧版本的 Token 即使没被清理也不能继续使用。

### Q5：登出后 Access Token 还能用吗？

回答：

> 当前 Access Token 是无状态的，登出后 Refresh Token 会立即失效，但已经签发的 Access Token 最长还能使用 15 分钟。这是短期 Token 的风险窗口。如果业务要求立即失效，可以在 JwtAuthFilter 里查 Redis 中的用户 version，代价是每个请求多一次 Redis 访问。

### Q6：怎么防止用户越权访问别人的数据？

回答：

> 后端统一通过 `CurrentUser` 获取当前用户。所有带 userId 的查询先做 `assertSelf`；新增记录强制覆盖为当前用户 ID，不信任请求体；删除记录先查归属再删除；资料更新使用白名单 DTO，不能修改 role/status/password；管理员接口统一 `/api/admin/**`。这些逻辑有跨用户访问 403 和伪造 userId 的集成测试。

### Q7：为什么血糖指标不用 AI 计算？

回答：

> 医疗数值必须可复现。TIR、TAR、TBR、CV、GMI 都用纯 Java Calculator 做，有窗口裁剪、脏数据过滤、样本量判断和明确舍入；AI 只做解释。样本不足返回 null，而不是 0，因为“没有足够数据”和“数值为 0”是不同语义。

### Q8：TIR、CV、GMI 分别是什么？

回答：

- TIR：血糖落在目标范围内的时间占比。
- CV：血糖变异系数，用标准差除以均值，反映波动性。
- GMI：根据平均血糖估算长期控制水平。

补充：

> 计算前会过滤生理范围外数据，时间窗口统一左闭右开，低血糖事件按时间归并，避免持续低血糖被重复计数。

### Q9：指标缓存怎么保证一致性？

回答：

> Key 里带用户维度和 version，数据变化时对 version 做 INCR。后续请求会生成新 key，旧缓存自然过期，不需要用 `KEYS` 扫描删除。Redis 失败时降级查 MySQL，主链路仍然可用，同时通过 `cache_error_total` 暴露被吞掉的缓存失败。

### Q10：每日聚合任务怎么防重复？

回答：

> 使用 Redisson 分布式锁，按日期加锁；拿不到锁直接跳过，不排队。每个用户复用同一个指标计算器，写入使用 MySQL `ON DUPLICATE KEY UPDATE`，保证任务重跑幂等。单用户失败不会中断整批。

### Q11：趋势中为什么还要今日实时兜底？

回答：

> 每日聚合在凌晨计算前一天，如果页面白天只读聚合表，就会缺少今天的数据。因此历史日期读取聚合表，今天直接用实时指标缓存计算，再按日期补齐空对象，保证前端日期轴连续。

### Q12：异步导出怎么保证不丢任务？

回答：

> 提交只落一条 PENDING，线程池执行前用条件更新把状态从 PENDING 改成 RUNNING。线程池满时使用 AbortPolicy，任务不会被 HTTP 线程同步执行；补偿任务每 30 秒扫描滞留 PENDING 并重新投递。多实例同时投递时，条件 claim 仍保证只有一个实例真正执行。

### Q13：如果进程在任务执行时挂了怎么办？

回答：

> RUNNING 超过 10 分钟会被标记 FAILED，不会自动重跑，因为旧线程可能还没完全退出。用户确认后再显式重试，最多 3 次。这样避免同一任务被两个线程同时写文件。

### Q14：为什么导出文件当前只能单副本？

回答：

> 文件写在本地 exports 目录。多副本时 A Pod 生成文件，下载可能路由到 B Pod，所以当前后端固定 1 个副本。生产级方案应换成共享 PVC、MinIO 或对象存储，再把任务状态和文件存储真正拆开。

### Q15：线程池参数怎么考虑？

回答：

> AI 调用是 I/O 密集型，核心 4、最大 10；持久化失败不影响主流程，所以使用独立小线程池；导出是后台任务，核心 2、最大 4，队列满时拒绝并交给补偿任务。关键不是背固定数字，而是根据任务属性、失败影响和拒绝后的兜底策略决定。

### Q16：SSE 流式 AI 的耗时怎么统计？

回答：

> 不能在 Controller 入口和返回处掐表，那样只测到“提交任务”的几十毫秒。我用 `Timer.Sample` 在流开始前计时，在流完成、超时或异常时统一停止，并按 scene 打标签，区分普通对话、血糖分析、饮食分析和每日小结。

### Q17：AI 对话上下文怎么管理？

回答：

> Redis 保存短期上下文，最多 20 条，每次只把最近 10 条发给模型，TTL 30 分钟；MySQL 保存长期历史。Redis/MySQL 持久化失败会被降级，不影响本次回复，同时有缓存和持久化失败指标。

### Q18：怎么降低 AI 幻觉风险？

回答：

> 第一，血糖指标由代码计算，模型只解释；第二，Prompt 明确不做诊断、不开处方，具体医疗建议提示咨询医生；第三，分析输入只使用后端查询到的用户数据；第四，数据不足时明确返回样本不足，不让模型补造。

### Q19：监控看什么？

回答：

- HTTP QPS/P95。
- AI 调用耗时、错误率。
- 缓存命中率和缓存失败。
- 日聚合任务耗时、失败用户数、上次成功时间。
- 导出任务积压、派发拒绝、失败率和 P95。

一句总结：

> 接口返回成功不代表系统健康，缓存降级、定时任务不跑、导出队列积压都可能“静默成功”，所以业务指标必须单独设计。

### Q20：上线前做了哪些安全处理？

回答：

> 生产 Profile 强制数据库、Redis、JWT、DashScope 和 CORS 使用外部配置；拒绝示例密钥和 localhost CORS；关闭 Swagger/Knife4j 和 SQL 调试日志；Actuator 独立到 9090，只暴露 health/prometheus；HTTP 生产入口必须使用 HTTPS 和 Secure Refresh Cookie。

### Q21：项目最大的技术难点是什么？

可以选择三项回答：

1. Refresh Token 并发轮换与主动吊销。
2. 异步导出任务在进程重启、线程池拒绝和多实例下的可靠性。
3. 医疗指标的可复现计算和缓存一致性。

不要只回答“接口多”或“页面复杂”。

### Q22：项目还有哪些不足？

回答：

> 第一，导出文件还是本地存储，后端不能水平扩容；第二，Access Token 主动失效有 15 分钟窗口；第三，AI 持久化只是异步旁路，极端情况下可能丢历史；第四，当前仍是模块化单体，适合当前规模，但高并发下需要拆分和分析型存储；第五，Kubernetes 清单已准备，但本地 kind 集群验收仍受环境阻塞。

## 4. 重点难点讲法：认证

推荐按顺序讲：

```text
问题：单个 24h JWT 风险窗口大，无法主动吊销
方案：15m Access JWT + 7d 随机 Refresh Cookie
存储：Redis 只存 Refresh Token 的 SHA-256
轮换：Lua GET+DEL，一次一换
并发：Lua 保证一个请求成功
吊销：user version + revokeAll
边界：Access Token 最长 15 分钟自然过期
```

## 5. 重点难点讲法：异步导出

```text
问题：同步生成 PDF/Excel 会拖慢 HTTP 请求，进程重启会丢任务
方案：数据库任务 + 线程池 + 补偿
领取：UPDATE ... WHERE status=PENDING
拒绝：AbortPolicy，任务保持 PENDING
补偿：30 秒扫描 PENDING
恢复：10 分钟 RUNNING 标 FAILED
幂等：多实例只有一个 claim 成功
边界：文件本地存储，当前单副本
```

## 6. 重点难点讲法：指标与 AI

```text
确定性代码：医疗数值
AI：解释、建议、自然语言
数据不足：返回 null / enough=false
缓存：版本号失效
AI 失败：降级，不影响关键数值
```

## 8. 面试官可能追问

### 如果 QPS 增加十倍

- 先看 HTTP P95、慢 SQL、连接池和 Redis 命中率。
- 读多写少的血糖趋势优先扩缓存和读写分离。
- AI 调用做队列、配额和异步任务。
- 导出拆独立 worker 和对象存储。
- 认证如果查 version 变重，可使用本地短缓存。

### 如果 Redis 挂了

- 认证：Refresh Token 无法轮换，用户需要重新登录或短时间继续使用 Access Token。
- 指标缓存：降级查 MySQL。
- 限流：应 fail-closed 或使用本地限流兜底，不能无限放行 AI。
- 日聚合锁：拿不到锁不执行，宁可跳过也不能多实例重复跑。

### 如果 MySQL 挂了

- 健康记录和聚合不可用，不能伪装成功。
- AI 可以返回系统繁忙，不应基于空数据生成结论。
- 导出任务保持 PENDING/FAILED，恢复后再重试。

### 如何设计数据库索引

- 所有健康明细都围绕 `user_id + 时间` 查询。
- `health_daily_glucose_stat` 使用 `(user_id, stat_date)` 唯一键。
- `export_task` 使用状态和创建时间支持补偿扫描。
- 查询必须带用户条件和时间范围，避免全表扫描。
